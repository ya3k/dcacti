## Objective

Implement resolution step 14 (Resolve Player Effects) per `GAME_RULES.md §17`: apply the HealPool generated by step 12 to the player's HP, clamped to MaxHP per `COMBAT_RULES.md §4`.

---

## Context

Steps 1–13 of the battle resolution pipeline are implemented. Step 12 (Generate Resources, TASK-018) produces a transient `HealPool` on `SwapExecutionResult.Resources` — the HP Gems cleared during the Match-3 cascade, converted at the documented per-Gem rate and match-tier multipliers (`COMBAT_RULES.md §2`). Step 14 consumes this pool to heal the player. `COMBAT_RULES.md §4` item 1 states: "Heal effects restore HP up to Max HP; overheal is discarded." No Relic or Status Effect modifies healing in MVP yet (§4 item 4 notes modifiers exist but none are implemented), so this step is a direct `min(HP + HealPool, MaxHP)` write. This is a pure state mutation — no new events, wire contracts, or systems are needed.

## Implementation Notes

- The HealPool is already generated and available on `SwapExecutionResult.Resources.HealPool`. The task adds a write step that reads this value and applies it to `PlayerState.HP`.
- Follow the same pattern as `ResourceGenerator.ApplyPower`: a pure static method that takes the previous `PlayerState` and the `ResourceGeneration`, and returns the updated `PlayerState`.
- The write belongs in the Domain layer (`GameServer.Domain/`), called from `SwapExecutor.Execute` in the same position as `ApplyPower` — after Resource Generation and before the single write-back.
- `COMBAT_RULES.md §4` item 1: "Heal effects restore HP up to Max HP; overheal is discarded." The formula is `HP = min(HP + HealPool, MaxHP)`. No other modifiers exist yet.
- The single write-back pattern (`GAME_STATE.md §5.1`) means `PlayerState.HP` is written in the same `with` expression as `PlayerState.Power`, `Combo`, `MatchCount`, etc. No separate write-back is needed.
- `GAME_EVENTS.md §2` has no healing event. No `BattleEventType` or wire contract changes are needed.

### Key Edge Cases

- `HealPool = 0` (no HP Gems cleared) → HP unchanged
- `HP + HealPool < MaxHP` → HP increased by full HealPool
- `HP + HealPool = MaxHP` → HP set to MaxHP exactly
- `HP + HealPool > MaxHP` → HP set to MaxHP (overheal discarded)
- `HP` already at `MaxHP` → HP unchanged regardless of HealPool
- Multiple cascades in one Swap accumulate HealPool → total applied once
- Healing is deterministic and draws no RNG

### Risks

- **The healed HP is not delivered to the client.** `SIGNALR_PROTOCOL.md` §4.2
  fixes the `playerState` payload member to exactly `combo` and `matchCount`, so a
  client cannot observe `HP` — neither its value nor this task's change to it.
  That is a protocol change owned by its own task; adding a wire member here would
  have exceeded this task's scope.
- **The Step-14 ordering is by construction, not by a runtime assertion.** The
  heal is applied after generation inside `Execute`, so the read of `HealPool` is
  ordered correctly by the code path. The two are independent writes to different
  fields, so the order does not in fact change the result
  (`PowerAndHp_ShouldBothBeWrittenByTheSameResolution` pins that they compose).
- **Healing has no consumer downstream, and no cost.** Because MVP implements no
  damaging step, a healed `HP` is currently only visible in state. The rule is
  nonetheless complete and pinned, so the later Damage/Boss stages read a value
  that already obeys §4 item 1.
