### Decisions this task resolves

**Decision A — `DurationTurns` semantics — DERIVABLE (document it; do not ask).**

Determination: `DurationTurns` is the number of Turns in the battle — sourced
from `BattleState.Turn` captured at the terminal resolution (already stated in
TASK-041's Implementation note). Under documented rules the three candidate
readings the audit raised (final `Turn` / count of committed Swaps / count of
Turns begun and completed) are **numerically identical**, so this is not an
`AGENTS.md` §20 ambiguous requirement — there are not multiple materially
different implementations to choose between.

Evidence (cite in the doc note, do not copy into other files):

- `docs/02-technical/GAME_STATE.md` §2.0.1–§2.0.2 — `Turn = 0` initially; no
  player Swap/Action has yet been successfully resolved.
- `docs/01-game-design/GAME_RULES.md` §2 item 1 — a Turn is a successfully
  resolved player Swap/Action.
- `docs/01-game-design/MATCH3_RULES.md` §8.1 items 1–5 — one committed Swap
  begins exactly one Turn; a rejected Swap begins no Turn; nothing else on the
  board begins a Turn; a Card cast begins no Turn. §8.3 fixes when the counter
  changes within the resolution.
- `docs/02-technical/GAME_EVENTS.md` §1 — the terminal resolution's ordering
  places `TurnEnded` **before** `BattleWon`/`BattleLost`, so the terminal Turn
  completes and is counted.
- `docs/01-game-design/CARD_RULES.md` §3 item 5 — a Card cast consumes no Turn.
- Corroboration only (not a source): `src/backend/GameServer.Domain/Match3/SwapExecution.cs`
  increments `Turn` once in the swap write-back, before the terminal HP checks
  in `src/backend/GameServer.Application/Battle/BattleStateService.cs` — a
  battle ending on its Nth committed Swap reads `Turn = N`.

Edge cases the doc note must state:

1. The terminal Turn **is** counted (per the `GAME_EVENTS.md` §1 ordering above).
2. A battle reaching a terminal state before any committed Swap ⇒ `0`.
3. `Sequence` (`MATCH3_RULES.md` §8.2, `GAME_STATE.md` §5.1) is a different
   counter and is **never** the source.
4. Source of truth is `BattleState.Turn` at battle end — not an event count.
   If a future action type is ever documented to begin a Turn, the value
   remains `BattleState.Turn`; only the swap-count equivalence could change.

**Decision B — `CompletedAt` provenance — DERIVABLE (document it; do not ask).**

Determination, by sub-point:

1. **Provenance:** generated by the server on the battle-end path; never
   client-supplied and never re-derived from client input or a session —
   `docs/01-game-design/GAME_RULES.md` §18, `docs/03-decisions/ADR/ADR-001-server-authoritative-battle.md`,
   `docs/02-technical/API_CONTRACTS.md` §7 item 1 (no client-submitted results),
   and the same never-from-client rule `DATABASE.md` §1 note item 2 applies to
   the sibling identity values.
2. **Instant:** the moment the battle reaches its terminal result and the
   durable result is written — `docs/02-technical/ARCHITECTURE.md` §4 item 4,
   `docs/02-technical/TDD.md` §4 item 2. One value per battle (one row per
   battle, `DATABASE.md` §1 note item 1).
3. **Role:** ordering key for `BattleResult(PlayerId, CompletedAt DESC)` —
   `DATABASE.md` §4 ("battle history, most recent first"); hence a server
   completion timestamp, not a content or client value.
4. **Type/timezone boundary:** no document specifies a timezone or column type,
   and `DATABASE.md`'s header states exact column types/migrations are an
   implementation detail (lines 43–45). The contract to document is therefore
   "server clock reading captured at battle completion" — **do not assert a
   timezone in the contract.** The absence of any `UTC` statement anywhere in
   `docs/` is a report-only item (§6 item 3), not a blocker.

**Decision C — `Outcome` vocabulary — HUMAN DECISION REQUIRED (`AGENTS.md` §4, §20).**

The conflict, both sources named:

- `docs/02-technical/DATABASE.md` §1 line 164 `Outcome ("Won" | "Lost")`, plus
  §1 contract note item 3 ("for both `Outcome`s … a `Lost` battle …").
- `docs/02-technical/API_CONTRACTS.md` §4 line 413 `"outcome": "Won" | "Lost"`
  and contract notes 1–3 (lines 429–438).
- `docs/02-technical/SIGNALR_PROTOCOL.md` §3.2.19 lines 821–844 — wire values
  `"victory"` / `"defeat"`, with note 1 claiming they are "the same names
  `GAME_EVENTS.md` §2 item 9 uses".
- `docs/02-technical/GAME_EVENTS.md` §2 lines 432–441 — defines the `Outcome`
  payload member but **no values**, and §2 contains **no item 9**. The
  SIGNALR cross-reference is false (already recorded as a follow-up in
  `tasks/completed/TASK-042-*.md` §6 item 1; this task is that follow-up).
- Current implementation/tests emit `"victory"`/`"defeat"`
  (`src/backend/GameServer.Api/Hubs/BattleEventWireProjection.cs` lines
  423–447; `tests/backend/GameServer.Api.Tests/BossWireProjectionTests.cs`,
  `BossResponseWireTests.cs`). No frontend reads the value; the REST endpoint
  and the `BattleResult` entity are not implemented yet.

Exact question for the human:

> Which vocabulary is authoritative for battle outcome across the four layers —
> persistence (`DATABASE.md`), REST (`API_CONTRACTS.md`), the SignalR wire
> (`SIGNALR_PROTOCOL.md`), and event-payload semantics (`GAME_EVENTS.md`)?

Options and consequences:

- **C-1 — single vocabulary `Won`/`Lost` everywhere.** Persistence and REST
  already use it, but the SignalR wire values, backend source, and tests must
  change → **not documentation-only**. Consequence: this task then only records
  the conflict and defers the wire change to a separate code task; TASK-041 is
  not unblocked by this task alone.
- **C-2 — single vocabulary `victory`/`defeat` everywhere.** Implementation and
  tests already match; requires editing `DATABASE.md` §1 and
  `API_CONTRACTS.md` §4 only → documentation-only. Consequence: the persisted
  and REST vocabulary becomes lowercase; no runtime break (neither is
  implemented/consumed yet).
- **C-3 — two documented vocabularies with an explicit mapping.**
  `GAME_EVENTS.md` §2 owns the semantic value set and the mapping;
  `SIGNALR_PROTOCOL.md` §3.2.19 documents the wire form, `DATABASE.md` §1 the
  persisted form, `API_CONTRACTS.md` §4 the REST form, each referencing the
  owner (per `GAME_EVENTS.md` §3 item 1 and
  `.ai/workflow/documentation/documentation-change.md` no-duplication) →
  documentation-only.

Ownership for the edit sequence (canonical owner first, then dependents):
`GAME_EVENTS.md` (semantics) → `SIGNALR_PROTOCOL.md` (wire schema) →
`DATABASE.md` (persistence) → `API_CONTRACTS.md` (REST).

Regardless of the option chosen, correcting the false
`GAME_EVENTS.md §2 item 9` cross-references in `SIGNALR_PROTOCOL.md`
§3.2.19 notes 1 and 3 is determinable and must be included.
